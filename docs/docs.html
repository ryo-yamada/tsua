Introduction

Repository: github.com/ryo-yamada/tsua

Tsua is a tiny, minimalistic HTTP server framework built on top of LuaSocket.

The framework allows you to simply serve files and send data over HTTP for something like a website, such as a portfolio, without messing with raw, low-level HTTP too much. It works similar to Express.js or Python's Flask.

Because Lua's runtime is pretty small compared to something like Python+Flask, tsua runs well on stuff like old devices, a tiny VPS, or a Raspberry Pi Zero W.

Currently, tsua is experimental and only encouraged for static websites where dynamic activity is limited. Security hardening is something I want to gladly work towards. When deploying publicly with tsua, it is recommended that you run it in a containerized environment like Docker.

Fun fact: this site is hosted with tsua!

Requirements

These are the criteria that must be met to use tsua:

  • A computer with an OS with a functional networking backend (Therefore microcontrollers won't work)
  • Lua runtime
  • LuaSocket (LuaRocks)
tsua is tested on Linux. It's probably functional on Windows and macOS too, but I haven't tested those platforms.

Minimal Application

This is what a minimal webserver with tsua could look like:

local Tsua = require("tsua") -- 1
local app = Tsua.new() -- 2

app:get("/", function(req, res) -- 3
    res:serve("./index.html") -- 4
end)

app:listen(19999) -- 5

Well, what does this code do?

  1. First, we require the tsua module file
  2. Then, we initialize a server instance to access tsua's functionality
  3. After that, we can compose a route (in this case, root) that takes GET requests
  4. This route then serves an index.html file that the client browser can display every time a GET request is made
  5. Finally, we set up the server to listen on a port, in this case port 19999.

You can then save this file as something like server.lua, and run it with lua server.lua. Make sure lua and luarocks is installed, and that luasocket is installed through luarocks aswell.

Static Files

Most web apps use static files for serving CSS, JS, images, etc. It's a way to serve files directly to the client without needing any specific route handling. Tsua makes it pretty simple. Create a directory called static, and place your desired files in it, for example, a style.css file.

In tsua, it would then be utilized and exposed like so:

app:static("/static", "./static")

And that's it! Tsua will now serve any static file(s) per usual, such as /static/style.css

The first argument is the URL prefix, and the second one is the directory's name on disk.

Just so you know, static directories are always checked before route handlers. If a path matches a registered static directory, the static file gets served, and the route handler will not be executed.

And as a side note, the directory name doesn't NEED to be static specifically. You could do something like app:static("/assets", "./public"), no problem.

HTTP methods

The currently supported HTTP methods are:

  • GET
  • POST
  • PUT
  • DELETE

Contrary to some belief, each HTTP method isn't really all that different from the next. It's just a way for the server to know what to do with the data presented/requested.

Note: POST and PUT both include URL-encoded bodies.

Routing

Creating routes allows clients to interact with your server in ways you define. Each route you make must be assigned an HTTP method and a path.

It's common practice for backend developers to compose a GET route on root (/) and to serve an index.html page on that route. This could be used as a home page.

Like so:

app:get("/", function(req, res)
    res:serve("./index.html")
    -- some other optional code
end)

It's important to know that the function in the route is a callback. So, whenever someone visits the root of your site on their browser, the code inside of the function will run. In the case above, the function's code serves an HTML file to the client that just connected.

Requests (req)

A request consists of data that a client sends when connecting or asking for resources on the server.

Naturally, this data can be parsed and manipulated and processed on the serverside however you want to. tsua helps you with this by providing the request's data as objects that you can access.

Here are all the request objects and example data:

app:post("/sendcredentials", function(req, res)
    req.method -- "POST"
    req.path -- "/sendcredentials"
    req.headers -- table of headers
    req.body -- "key1=abc&key2=123"
    req.params.key1 -- "abc"
    req.query.name -- /sendcredentials?name=ryo -> "ryo"
end)

And here are descriptions for each object:

  • req.method stores a string of the method type. Simple as that. Could be GET, POST, PUT, or whatever else tsua supports.
  • req.path stores a string of the path of the request. Could be root ("/") or a specific page ("/blog/my-first-post")
  • req.headers stores a table with a bunch of headers that the client could have sent. If no headers are sent, this table is empty.
  • req.body (POST/PUT ONLY) stores the body of the request. This body could be pretty much anything as long as it's URL-encoded. It should be noted that the server should have code to accept and process bodies.
  • req.params is pretty much an abstraction of req.body. It's populated with the objects of the URL-encoded POST and PUT body requests.
  • req.query is populated by parameters in the URL query string.

Note: header names (req.headers) are converted to lower case by tsua

EDGE CASE:

There's also a req.dyn object that is only usable when dynamic routing is used. This means that, when a route is registered using the dynamic routing syntax, (e.g. /<page>) you'll be able to access and read the requested path like so: req.dyn.page

Responses (res)

When a client connects and sends a request, you obviously need to respond, or else the client won't receive anything on their end whatsoever. So, tsua has a couple of helper functions implemented that make responding to a client easy. Each function serves their own purpose.

res:send()

This function is pretty self-explanatory. It sends any data when a client connects. Matter of fact, every other function that sends data (res:serve(), res:redirect(), ...) uses this function internally. It'd be pretty messy and annoying to write an instruction to redirect every time you want to, after all!

Here's an example of how you'd use this function:

app:get("/hello", function(req, res)
    res:send("200 OK", { ["Content-Type"] = "text/html; charset=UTF-8" }, "<h1>Hello from tsua</h1>")
end)

The first argument is the status code. Ideally, it should include the number-based status-code, and the text-based status-code.

The second argument is the headers table. In the example above, the only header that is sent is the Content-Type header, which tells the browser or client what type of data the server sent. In this case, it's basic HTML in UTF-8 format. A browser would receive this and render the received HTML.

The third argument is the actual data. Since the Content-Type is HTML in UTF-8, that's the type of data you'll have to pass through. In the case above, a simple header with some text would be received by the client's browser.

res:serve()

This function is alot more useful for websites. It reads a file from disk, and then serves it to a client that connects. This means that you can have an HTML file on your disk and pass the path of that file into the function, and the page would render on the client's browser.

Like so:

app:get("/", function(req, res)
    res:serve("index.html")
end)

That's pretty much all you have to do.

res:redirect()

This function is useful for when you want to redirect clients that connect with their browser from one page to another. That's about it.

Here's an example:

app:get("/old-page", function(req, res)
    res:redirect("/new-page")
end)

Simple, right? There's only 1 argument, and it expects the path of the route you want to redirect a client to.

Internally, it sends a 301 Moved Permanently status.

res:json()

This function is a bit more special. It's useful for building an API, but tsua does not and will not implement a json encoder. Therefore, you'll have to bring your own function and plug it in. It could be a function from a library, or your own personal function. Up to you.

This is how you'd use it:

app:get("/api", function(req, res)
    res:json(your_encode_function, some_data_in_table)
end)

The first argument would be the json encoder function you obtained from anywhere.

The second argument is the actual data you want to encode and send. This data's format must be a table.

There's also an optional third argument, which is a status code you'd like to send to the client. If this is not supplied, it'll send a simple 200 OK.

res.escape()

This is less of a function that interacts with the client, but moreso with the data that you're planning to send, before you send it. It's recommended to apply this to user-supplied data before including it in any sort of HTML response, because otherwise you could send data in a format that you didn't expect to send.

It's used like so:

app:get("/hello", function(req, res)
    res:send("200 OK", { ["Content-Type"] = "text/html; charset=UTF-8" }, res.escape("<thingymajig>"))
end)

In the case above, if the data in the function wasn't escaped first, the client's browser would receive it and get confused by assuming the "<thingymajig>" string is an HTML tag, and then it would error or just not display.

Configuration

You can configure an instance from the framework and fine-tune it to how you want to. Here's an example of how you'd configure an instance, pay attention to the initialization:

local Tsua = require("tsua")
local app = Tsua.new({ -- init & config
    max_headers = 15,
    timeout = 2,
    not_found = "./frontend/404.html"
})

app:static("/static", "./static")

app:get("/", function(req, res)
    res:serve("./frontend/index.html")
end)

These are all the configurable options, an occasional short description and their defaults:

request_logging = config.request_logging ~= false, -- looks weird but it prevents unexpected behavior when setting a config, default is true
max_body = config.max_body or (1024 * 1024), -- 1MB default max body in requests
max_headers = config.max_headers or 30, -- default 30 max headers possible in requests
timeout = config.timeout or 3, -- default 3s before dropping client
error_handler = config.error_handler, -- custom error handler function config
not_found = config.not_found,  -- path to a custom 404 html file, default is framework-provided page
forbidden = config.forbidden, -- path to a custom 403 html file, default is framework-provided page
internal_error = config.internal_error, -- path to a custom 500 html file, default is framework-provided page

Contributing

Contribution is heavily encouraged, and I'm trying to keep tsua small and approachable for this reason

If you are:

  • learning lua
  • interested in HTTP
  • looking for something to contribute to

then I'm looking forward to working with you.

Issues, pull requests, feature suggestions, and discussion are all appreciated. If you're looking to contribute but aren't sure how, you can check the issue tracker, in which I or others might post some issues for you to look into.

Development is currently focused on:

  • Core functionality
  • Developer experience enhancements

Philosophy

This was a project I started just for fun, as I wanted to see how easy it would be to deliver a site over the web with a Lua backend. However, it started becoming its own little framework, and so I decided to publish it on GitHub. My plan is to continue developing it with a focus on simplicity.

This framework is aimed towards sites that don't have too much dynamic functionality. Portfolios, documentation, etc. However, I suppose when this framework continues development, it will probably be able to support more dynamic functionality.

Security Policy

If you think you've found a vulnerability for tsua, please reach out to me at f@placeq.com, and we'll continue speaking there.

When sending me an email, please provide details in the following structure:

  • Description of the issue
  • How to reproduce
  • Potential impact
  • Suggested fix, if available

Please do not publicly report or discuss security vulnerabilities.
